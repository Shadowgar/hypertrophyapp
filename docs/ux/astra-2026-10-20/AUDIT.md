# Astra UX audit — 20 October 2026

**Status: audit complete within the agreed evidence scope; sketches are proposals for owner review. No implementation, migration, deployment or release acceptance.**

The largest problems concern trust during ordinary tasks: signing in through onboarding can enter a profile-replacement pipeline; saving equipment can clear unrelated constraints; working-set errors disappear behind the runner; and History calls rest days “Missed.” The rendered exercise flow also requires substantial scrolling before logging and moves the next input after acknowledgement. These need more than visual polish, while preserving the application's existing mode, consent and performed-evidence boundaries.

## Method and evidence

This is a fresh Astra synthesis of two independent `gpt-6-astra` source audits, a separate rendered-browser audit, and a second source verification of the two profile-write findings. Prior Medium audit/design artifacts, including Focus/Training Ledger, were not consulted or reused.

The source baseline is **`fc3bd0c7b93c9d3232e6aec758e16efcca6ac583`**. The deployed login footer identified **`d60d9ed413329f575947568c05888546f8d3e6d5`**. The browser auditor verified an empty `apps/web` diff between those revisions; this connects the inspected frontend source to the deployed presentation, but does **not** establish the deployed backend revision or persistence behavior.

Browser: deployed frontend at `https://hypertrophy.theroccos.us`, Chromium, **390 × 844** and **1440 × 900**. Guest pages used live responses. The owner explicitly selected clearly labeled synthetic journeys rather than an authenticated disposable backend. Signed-in screens used intercepted synthetic API responses and a synthetic session; no real credentials, account, workout records or database were used. No destructive controls, real acceptance or schedule activation were exercised. Static inspection did not run tests, imports, services or migrations.

## End-to-end journey readout

These sequences cover the full user intent. Arrows describe source flow unless a rendered interaction is explicitly identified; they do not assert completed backend transactions.

1. **Join and begin training:** Home → onboarding welcome → 16 questions → account/program choice → registration/profile save → recommendation where applicable → initial generation/review → Today → Week to select actual dates. Guest entry is LIVE; downstream writes are SOURCE. Defaults and swallowed errors obscure whether setup produced a usable plan (F11/F24). Choosing the explicit Customized program branches to `/customize` after profile save.
2. **Return or recover:** dedicated Login → token → requested path/Today; Forgot Password → request email → token/new password → confirmation → Login. Guest presentation is LIVE; email/auth lifecycle is untested. The separate onboarding “already have an account” route joins profile setup writes (F01), not merely authentication. Query-preserving return and visible sign-out are missing from the inspected UI (F18).
3. **Choose mode and equipment:** onboarding/Settings/Week program controls → Authored selection or explicit Customized entry; basic equipment lives in onboarding/Settings, precise inventory in Customize. The labels are inconsistent (F13/F15); Settings's narrow edit reaches the full-profile overwrite path (F02). Authored phases and Customized must remain distinct.
4. **Schedule Authored training:** Plan → current/next week → timezone + 2–5 local dates → preview → workload/session review → Activate → Today. Dates and preview presentation were SYNTHETIC; activation was not performed. Digest/revision validation and stale-preview invalidation are SOURCE strengths. Workload evidence should inform activation rather than trail it (F14).
5. **Design Customized training:** Customize → bounded authority/context → inventory/constraints → exactly three dates → preview/comparison → acknowledgement → Accept version → Activate selected dates → Today. Synthetic checkbox gating was verified: Accept disabled before acknowledgement and enabled afterward. Neither Accept nor Activate was clicked. Replacement and date amendment remain different source paths with distinct confirmations.
6. **Execute an Authored session:** Today → exercise → source prescription/warm-ups → actual warm-up save → actual working reps/load/effort → acknowledgement → receipt + rest → next set → exercise/session progress. A fixture warm-up and work set (12 reps, entered 40 lb, actual RPE 8) were acknowledged synthetically. A subsequent fixture journey acknowledged three work sets, displayed All Sets Complete and 1→2→3 receipt Edit buttons, corrected set 1 to 11 reps, undid set 3, then reloaded/reopened into two receipts with set 1 at 11 reps and working counter Set 3/3. Logging depth, 90 px motion, unit switches and error invisibility were observed (F03–F07). Source correction replaces effective evidence; Undo refetches Today/Progress. The synthetic reload verifies frontend hydration from in-memory fixture state only; durable backend persistence, reconciliation and concurrency remain unqualified.
7. **Execute Customized training:** active Customized Today → exercise → owned kg/load options and RIR/technique/pain fields → save → next set. Synthetic runner presentation was inspected; mode-specific input distinctions exist, but calibration prose/receipt headings precede logging. Incomplete fixture basis fields are excluded from defects. No client-invented load or progression rule is proposed.
8. **Review and continue:** History → date/detail/charts → Check-In/Sunday Review → review result → dated users return to Week; legacy path can generate the next week. Synthetic empty calendar/review presentation exposed misleading labels and units; actual history/review writes were not tested. Source calendar semantics, receipt omissions and response ordering remain consequential (F08/F09/F16/F20/F21).
9. **Learn and return:** guide library → program → phase → day → exercise; alternative program/legacy day routes also render. Synthetic navigation covered all seven guide-related patterns. Library discovery and JSON presentation impede this otherwise useful information path (F18/F28); real source content and licensing were preserved.

## Boundaries the sketches must preserve

The following are **SOURCE-supported protections**, with only the explicit consent checkbox additionally checked in SYNTHETIC rendering: occurrence-scoped identities; immutable retry payloads; unknown actual effort remaining unknown; canonical kg and actual receipts separate from advice; warm-up counts separate from working completion; correction/undo rebuilding effective evidence; selected-date preview/revision checks; and explicit Customized preview, acceptance and activation stages. Current labels and spacing can change without discarding these protections.

Authored Phase 1, Authored Phase 2 and Customized remain separate. Source prescriptions retain authority; source-approved substitutions require confirmation. AI, explanations, layout and convenience defaults gain no prescription-mutation authority. Equipment changes do not silently redesign accepted programs. Missing evidence stays missing; no invented RPE, reasons, readiness, duration guarantees or causal interpretation. Metadata scoring stays frozen. A persisted unit preference or Authored known-1RM input shown in a sketch must be marked **PROPOSED capability**, not an existing API or a presentation-only patch.
