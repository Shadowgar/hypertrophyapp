## Ownership and transaction

`LifecycleService` still owns commands/consent. Its authorization callback is constructor-owned and read-only; the existing staging factory rejects a supplied service whose callback belongs to another gate. It does not assign authorization state. Distinct hosts cannot overwrite one shared service's gate. Unconfigured routes deny by default. The optional actor-bound store transaction preserves existing isolated SQLite compatibility.

`PostgresUnit` owns the PostgreSQL connection context per instance and execution context. It locks the existing `users` row before grant, calendar and candidate access, matching #83/history's `lock_history_user`. The lock remains held through revision append and command receipt commit. Different subjects lock different rows. Credential UPDATE itself conflicts on this same row; grant/session revocation must use this User-first protocol too. The adapter's server-side `revoke` does so. Tests observe independent competing writers actually waiting on a PostgreSQL lock, in both acceptance and historical-retry paths. A command winning first may commit before revocation; after revocation commits, old actors and cached retries fail. This is serialization, not retroactive erasure of an earlier valid acceptance.

`PostgresSessionGate` stores a server-generated UUID session, token credential fingerprint, current credential digest, monotonically changed grant revision, subject, explicit entitlement reference, server scopes and validity/revocation. A fingerprint is only a lookup credential; it cannot create a session or scope. The existing JWT signature/expiry/current User verifier remains the identity bridge. Trusted server provisioning is explicit and unregistered. No client claim can provision a grant. Rotation/reset tests use the same database lock and retained grant revision; password changes also invalidate mismatched credential digests. No app-wide JWT/login/reset route is modified. Production provisioning/rotation/reset hooks, session retention and device/key ownership remain a release integration requirement.

## Additive candidate persistence

Five candidate-only relations implement the existing transaction port: schema version, server sessions, immutable candidate event documents, current revision/digest heads and idempotency command receipts. Consent receipts and the complete audit stay inside immutable event JSON; no second consent model is introduced. Compound account keys, User FKs, unique command keys and head-to-event FK constrain ownership/revision identity. API queries are account-qualified; unknown/foreign objects return404.

Event documents form a canonical hash chain. Replay verifies subject/proposal/revision continuity, every document digest and the independently persisted final head. Append and head CAS occur in one locked transaction. This detects a missing tail that would otherwise expose an older accepted state after withdrawal. A completely coordinated rollback of the database and all checkpoints requires external recovery/version controls; this ledger does not claim to detect it. Runtime database privileges and operational checkpoints require release qualification; the rehearsal owner role is not a production least-privilege claim.

The additive SQL lives **outside production Alembic**, in `research/m4c3b2b/001_candidate_integration.sql`, behind explicit disposable-target tooling. Existing User/Authored/history schemas are neither altered nor reset. The target guard requires an explicit `/tmp` manifest, loopback host, exact role/DB allowlist and random out-of-band marker plus database/user verification. Bootstrap additionally checks owned container ID/label/temporary mounts and an empty database before named source-table copies and migration. No inherited DATABASE_URL selects the PostgreSQL target.

## Calendar source status

`SourceCalendarPort` reads actual existing ORM table shapes: `WorkoutPlan`, `WorkoutOccurrence`, `WorkoutSetLog`, `WorkoutLogCommand`, `WorkoutSessionState`, plus User ownership/lock. It reuses `workout_identity.identified_sessions` for stable plan/session/exercise identities, including duplicate catalog exercises. The source reference is #83 head **3f4927b3cdcca1e8655337b30b93894741bfca9c**. Models, history/identity helpers and these table shapes are unchanged on that head. Its selected-date command locks User, uses `placement_revision`, marks displaced plans `selected_dates_superseded_v1` and rejects any execution/consent snapshot in the target week. Its current/next-week resolver and generation/activation dependencies are **not imported or copied into this stack**.

This read projection binds preceding/selected/following weeks, dated plan payloads/placement, retained snapshots, all relevant effective/void/amendment rows, undone commands and session state into freshness. Snapshot existence remains frozen after every set is undone. Session state is a conservative projection of effective ordinary work, not new prescription authority. Missing/empty/mismatched dated coverage is incomplete; conflicting active rows or frozen date/revision disagreement fail closed. It never rewrites source payloads, dates, slots or performed evidence.
