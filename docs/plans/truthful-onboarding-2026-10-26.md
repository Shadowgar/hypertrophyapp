# Truthful registration and history preservation

Owner-authorized implementation, 2026-10-26; isolated candidate based on main `ad789ff983a51c2445fde34c849d3738fcb0311a`. This is the bounded onboarding integrity package from the engineering/backlog assignment, not a new product roadmap or release approval. [Onboarding contract](../contracts/onboarding-profile.md), [personal direction](../requirements/personal-workoutapp-2026-10-21.md), [execution/history contract](../contracts/execution-plan.md), [selected-date scheduling](../contracts/selected-date-scheduling.md) and [evidence](../evidence/onboarding-2026-10-26/README.md) govern its limits.

## Behavior

- Registration never writes an inferred nutrition phase, fixed macros, adherence, recovery or an automatic weekly review. Optional values explicitly entered by the user are profile **targets**, not observed intake. Existing nullable database columns retain unknowns as `null`; no migration or historical repair is performed. Omitted targets preserve prior saved targets.
- New-account setup uses `/profile/initial-setup`. The existing account lock serializes a check of raw nullable training fields with the first save. Registration identity/default manual mode is not a training profile; a partial profile, Auto preference, empty equipment list or explicit zero target is not a blank profile. Repeated/late initialization returns 409 instead of overwriting saved settings. Normal `/profile` remains available to explicit compatibility/settings clients.
- Login remains authentication only. Failed setup can retry for the same newly created token/email. Reload recovery is an explicit read of the signed-in profile: re-enter private questionnaire fields for a blank account, or continue the saved selection after a successful save/lost response. The shell preserves onboarding during its own registration handoff; onboarding explicitly remounts and clears its draft on any external account change. A response from an earlier account cannot install a token, navigate, write another profile or replace the current recovery message. No additional token/health draft persistence is introduced.
- Choose for me remains `auto` without frontend recommendation/switch policy. Explicit Authored preference proceeds to Week's existing dated preview/activation. Explicit Customized proceeds to `/customize`, where its existing consent owner decides activation. Registration neither creates a legacy week nor retries failed generation behind a success message.
- The scheduling clock still gates Today. An absent, failed or pending weekly review does not block an already scheduled workout. Daily soreness date checks, occurrence verification, stationary entry and immutable command recovery are retained. A due weekly report is offered in Check-In rather than fabricated during onboarding.
- Ordinary profile, answer or confirmed program-preference changes no longer call the training-state deletion helper. Dated plans, receipts, corrections, reported check-ins and generated onboarding consent remain intact. The two explicit development reset/wipe paths keep their existing backend authorization/confirmation/default-off safeguards. Their onboarding controls require an explicit development build opt-in and are absent from production builds.

## Qualification and boundaries

Use verified disposable SQLite/PostgreSQL and synthetic browser accounts only. Cover unknown/explicit nutrition, existing login, Auto/Authored/Customized selection, failed save, lost response, reload, late error bodies/account switches, concurrent initialization, preserved history and unavailable review/generation. Preserve existing tests except documented obsolete expectations for invented nutrition defaults and the removed Sunday hard gate. No source prescriptions, numerical load policy, Customized consent policy, migration, production data, merge or deployment are authorized by this package.

The full approved onboarding visual replacement remains a subsequent slice. Existing historical fabricated records are left untouched; reconciliation of those records requires a separately reviewed procedure.
