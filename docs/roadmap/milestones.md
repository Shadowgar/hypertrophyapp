### Cross-milestone UX delivery: M4 gym usability → M6 full application redesign (2026-10-20)

The owner requested an **ASTRA-led UX audit and redesign of the entire WorkoutApp**, not another external review or change to the training engine. This work is inside the **existing M6** user-experience/mobile/reliability scope and is tracked by [#105](https://github.com/Shadowgar/hypertrophyapp/issues/105); it is not a new top-level milestone.

- **Immediately alongside finishing M4:** repair the firsthand iPhone gym-use failures in [#103](https://github.com/Shadowgar/hypertrophyapp/issues/103): two-minute apparent blank workout after reload, inconsistent kg/lb input and absent unit preference, missing discoverable known-1RM initial guidance, mobile set-save jump and duplicate set status above/below input, overwhelming advanced equipment/effort screens, warm-up language and unclear 29-set session heading. Preserve actual logged data, Authored source, existing intelligence and canonical-unit consistency. Don't defer a necessary working-set usability correction until broader M6.
- **M6-Audit/Redesign:** using ASTRA where selectable, inspect the **actual running** account/onboarding, Home/navigation, Authored/Customized choices, equipment/location, Week, Today/exercise modal, Check-In, History, Analytics, Settings, errors/recovery and accessibility on iPhone Safari and desktop. Inventory every screen, user decision, default, load state and failure mode; create cohesive visual/interaction patterns and before/after task flows. Improve actual usability rather than merely the color scheme.
- **M6-Implementation:** implement the redesigned experience through focused PRs and existing application components, without a second planner, second schedule engine, data migration by default, or changed medical/scientific claims. Verify set logging, correction/undo, progress, timer, consent, account switches, offline/retry boundaries and state preservation. Each bounded, authorized delivery can land when safe; the whole redesign need not block earlier gym repairs.
- **Evidence:** demonstrate distinct real first-use and returning-user paths for Authored Full Body Phase 1/2 and Customized, with real iPhone-like keyboard/scroll/safe-area behavior, saved lb/kg preference, no shifting input after a confirmed set, timed load/reload before-after results and useful accessibility/visual tests. No claim that ASTRA was used unless the coder selected it.

This is an **owner-requested roadmap placement**, not production deployment authorization. Keep work sequenced against existing M4 and M6 requirements, [product contract](../requirements/product-contract.md), [flow requirements](../ux/flows.md) and [data-safety lock](../../DB_SAFETY_LOCK.md); no outside UX/science consultant or new roadmap is a prerequisite.

GEN-008 wider splits, DATA-006 export and DATA-007 data-quality inbox remain proposed/deferred; allocate a future bounded package after their dependency/owner review. AUTH-FID-008 integrity view, SCHED-008 feasibility preview and REC-004 outcome review are proposals, not implicit global release blockers. The catalog retains all original features even where implementation is partial.

## Evidence, gates and decisions

A milestone requires goal/scope/requirements, dependency resolution, relevant automated and manual criteria, revision/environment/artifact-linked evidence, reviewed deviations and explicit owner acceptance. A plan, published document or passing subset is insufficient. Gate applicability follows controlling safety/mode/source/history invariants for changed/enabled capabilities; do not silently turn every feature proposal into a blocker.

The [evidence registry](../evidence/README.md#recorded-audit-baseline) preserves core 364/4, original API 430/18/8, selected recheck 12 passes, six behavioral API failures, web 51/1 and 102 test-global type diagnostics with isolation/snapshot limitations. No new runtime results supersede them.

Unresolved owner decisions before affected implementation: recovery availability/legacy JWT cutover; licensed source-fixture retention and source-approved-option ambiguities; legacy mode/occurrence/unit mapping; correction storage/concurrency strategy; started-date/carryover policy and local-week default; progression/comparability/confidence/spacing rules; operational RPO/RTO/ownership and session/ingress strategy; longitudinal protocol; target devices/offline scope. Desired outcomes and parallel ordering are established, while numerical mechanisms and release acceptance remain pending.

The completed, owner-reviewed documentation migration is recorded in the [authority migration report](../audits/2026-09-28-documentation-authority-migration.md). Select subsequent work through an explicitly authorized bounded package; documentation approval does not authorize runtime changes, deployment or database migration. Use the [single plan registry](../plans/README.md); historical next-task scripts and old roadmap checkmarks confer no authority. Remaining implementation detail requires separately bounded plans and approval.
