## Implemented boundary

[API identity owner](../../apps/api/app/workout_identity.py) derives UUIDv5 from
user ID, persisted plan ID, week start and zero-based session slot. A new plan
revision gets new occurrences. Reopening an existing plan retains its IDs.
Each exercise UUIDv5 derives from that workout UUID and its execution-slot
index; catalog/primary IDs remain separate. Identity decoration is on response
copies, not authored templates or persisted program artifacts.

The first successful log freezes the session prescription and plan/week/slot
lineage in WorkoutOccurrence. Explicit occurrence routes can read that snapshot
after a replaceable WorkoutPlan disappears. The snapshot does not certify
immutable source/rule versions or implement a rescheduling/revision lifecycle.

[Models](../../apps/api/app/models.py) add nullable identity to old log/state
tables, occurrence session-state uniqueness, a partial legacy uniqueness index,
and a retained WorkoutLogCommand ledger. No historical identity backfill occurs.
Unidentified history remains stored but does not supply current occurrence
completion, resume, guidance, summary or undo. A legacy template route resolves
only the unique matching slot in the latest plan; ambiguous slots conflict.
Explicit workout UUIDs and exercise UUIDs are the modern client contract.
Missing command IDs use a compatibility command for one logical slot; repeated
catalog slots still require explicit exercise occurrence. Compatibility retries
after undo return the original result; a new attempt needs a new explicit ID.
Performed-variant consent/modeling and uncertain legacy provenance remain open.

[Logging transaction](../../apps/api/app/routers/workout.py) locks the user's row
on PostgreSQL. Record, existing progression update, session projection and
normalized SHA-256 request digest/result commit together. User/command uniqueness
is enforced in both ledger and log tables. Digest includes the supplied workout
reference and normalized typed payload, including exercise occurrence. Identical
retry returns the persisted original response; a changed payload conflicts
before mutation. The ledger retains original results and an undo timestamp even
after set removal, so a delayed retry cannot resurrect the set. Legacy template
and UUID route spellings are different command inputs.

Today/progress/summary/resume use occurrence keys. Plan regeneration protection
checks identified records against the target plan; unresolved legacy history
retains conservative protection. This is not concurrent plan-revision/cutover
qualification. Pure core inputs without new identity preserve legacy shapes.

[Today](../../apps/web/app/today/page.tsx) uses workout/exercise occurrence keys
for counts, swaps, selection, hints and timers. Version-2 caches ignore old
template caches. An API response without occurrence identity gets an ephemeral
view cache namespace, not restored template state. Pending command IDs survive
failed submissions and browser storage; a failed save does not advance a set.
Simultaneous clicks are one pending attempt. Late responses are guarded from
updating a different displayed occurrence. Week list keys also use occurrences.

Undo removes only the latest timestamp/ID-ordered set inside the requested
user/workout/exercise occurrence. **ExerciseState exposure/streak/fatigue/load
effects still remain stale after undo.** Session replay still uses the existing
reducer, including its technique/correction limits. Full correction history,
deterministic ExerciseState reconstruction, logical exposure semantics, revision
transitions and broader history analytics belong to later M0-HIST work. No M2A
load policy or SEC-S2 behavior is implemented here.

## PR #39 follow-up qualification

The authorized wipe paths now remove commands, occurrence-dependent sets/session
states, then occurrences before user deletion. SQLite with FK enforcement and
migrated PostgreSQL verify both paths and preservation of another user's history.
Distinct command IDs for the same occurrence/exercise/set-kind/parent/technique
ordinal slot conflict under the existing user-row lock. Identical command retries
still replay; undo permits a new explicit attempt. A PostgreSQL barrier test
qualifies distinct-command contention for one logical slot (200/409, one log).
No active duplicate is admitted by these routes; command uniqueness remains the
existing database constraint, and the logical-slot gate is transaction-locked.

determinism 1 passed. The latter compares every prescription/metadata field,
excluding only plan and occurrence IDs that differ intentionally across new
