## Storage and deterministic decision ownership

[Migration 0020](../../apps/api/alembic/versions/0020_workout_set_amendments.py)
adds nullable void timestamp/reason/source, amendment timestamp, unique
self-reference `supersedes_id`, and replay-context JSON. No historical fields,
identity or effort are backfilled. Undo annotates a void; correction appends a
replacement. Original reps, weight, RPE, set identity and receipt time remain
unchanged. Replacement receipt time preserves original replay ordering;
`amended_at` records the actual correction time. Receipt time is not proof of
performed time. The audit endpoint is user-scoped and does not expose captured
profile/rule payloads.

[API replay orchestration](../../apps/api/app/workout_history.py) calls the
existing `core_engine.prepare_workout_log_set_decision_route_runtime` and
`resolve_workout_session_state_update`. Actual request/plan/rules/profile inputs
and the pre-log projection are captured at logging. Effective records replay in
original root receipt/ID order. All five progression fields are rebuilt;
`last_updated_at` becomes the latest effective receipt, or the captured baseline
time. If no prior projection or effective record remains, only the derived
ExerciseState row is removed. Unknown earlier history remains represented by the
actual captured baseline and an explicit trace flag, not invented records/RPE.
Intersecting uncaptured history or missing reconstruction context returns 409
and rolls back the amendment/projection changes.

The requested workout/exercise occurrence session is replayed from effective
ordinary root working sets. Warmups/technique children remain stored/auditable
but do not replace root working-set counts or exposure effects. Counts use
actual distinct identified slots rather than inferring missing sets from the
maximum index. Pure legacy core input behavior remains compatible.

Logging and history actions lock the same user's row before mutation. The shared
ledger stores normalized action digests/results. Old log retries replay their
original receipt without restoring history; identical action retries replay,
changed input conflicts. Correction and its projections commit atomically.

History, Today, progress/summary, review signals and future recommendations query
effective records. Later previews and review summaries are conservatively marked
invalid after a correction/undo; payloads and applied decision records remain.
Invalid previews cannot be applied and invalid review summaries are excluded
from future consumers. This does not reverse previously applied choices or
rewrite authored/generated prescriptions. Plan lineage/deletion protection still
retains audit history, including voids.

The [web undo flow](../../apps/web/app/today/page.tsx) retains one command across
lost acknowledgement, prevents simultaneous undo, waits for confirmation and
refreshes server counts and load guidance. An old occurrence response cannot
update a different displayed occurrence. There is an API correction client;
a dedicated correction UI is still future work.
